# Who this playbook is for

The same accessibility requirement needs different information depending on the
reader's role.

| Audience | What they need from the playbook |
| --- | --- |
| Executive sponsors | Risk, accountability, outcomes and governance |
| Product owners | Requirements, Definition of Done, prioritisation and release implications |
| Business analysts | User needs and testable acceptance criteria |
| Delivery managers | Lifecycle checkpoints, dependencies, escalation and evidence |
| Designers | Interaction, visual and content requirements before build |
| Developers | Implementation guidance, code patterns and remediation |
| QA / accessibility testers | Repeatable test methods, expected results and severity |
| UAT | User-journey scenarios and escalation routes |
| Design systems | Reusable patterns and component specifications |
| Legal / risk / compliance | Standards context, exceptions and governance evidence |
| Procurement | Consistent expectations for suppliers and platforms |
| Learning teams | Role-specific enablement and training pathways |

A mature playbook does not expect every reader to become an accessibility specialist.
It gives each role enough information to perform its responsibilities and shows when
specialist input is needed.

Content designers should start with [error handling](/design/error-handling).
Technical leads and architects should review [the lifecycle](/operating-model/delivery-lifecycle)
and [development guidance](/development). Accessibility specialists should start with
the [testing baseline](/standards/testing-baseline) and [ownership model](/operating-model/roles-and-responsibilities).
