# How to use the playbook

## Requirement language

- **Must** means the playbook treats the item as required.
- **Should** means it is strongly recommended unless there is a justified reason not to use it.
- **May** describes an optional approach.

## Page metadata

Technical guidance pages identify their **audience**, **purpose**, **when to use** and
**owner** near the top. This helps readers decide quickly whether a page is relevant.

## Do not use this as a checklist-only compliance exercise

A checklist can support repeatability, but accessibility requires professional
judgement, user-impact analysis and testing across realistic user journeys.

## Follow a task

For a new form, start with [form design](/design/forms), agree the
[component behaviour](/components/form-fields), write [acceptance criteria](/delivery/acceptance-criteria)
and collect a [test record](/resources/templates). If it fails, use
[remediation](/remediation) and the [release gate](/delivery/release-gates).

Use the sidebar for sections, the page contents for headings and search for a task
or component name. The [case study](/getting-started/case-study) explains why policy,
specifications, patterns, tests and training remain distinct.
